# Coverage and PA reconciliation policy — Phase 0.0-E

Coverage is an assessment of a **specific game/domain/revision**, not a synonym for HTTP success or `Game.finality`. Current `GameDataCoverage` is a projection of append-only assessments. `COMPLETE` is granted only by positive proof. `PARTIAL` means evidence exists but is demonstrably missing/conflicting; `UNKNOWN` means the evidence is insufficient to decide; `UNAVAILABLE` means the required source is explicitly unavailable under the approved access/retention policy. Reassessment can move either direction. A final game can be PA `PARTIAL` and HR `UNKNOWN`.

## Conservative game status/finality mapping

Provider fields must be read together. The table covers **sampled** codes and safe unknown behavior; no broader code taxonomy is asserted.

| Observed source fields | Canonical status | Finality | Confidence / evidence |
| --- | --- | --- | --- |
| `codedGameState=F`, `statusCode=F`, `detailedState=Final`, with matching game identity and no contradictory postponed/suspended indicator | `COMPLETED` | `FINAL` | High for sampled 746656 after reschedule and 746977; E18/E04. A feed may still be incomplete. |
| `codedGameState=D`, `statusCode=DI`, `detailedState=Postponed` even when `abstractGameState=Final` | `POSTPONED` | `NOT_FINAL` | High for sampled April 12 schedule 746656, E05/E18. |
| Explicit observed scheduled/in-progress/suspended/cancelled/rescheduled detailed state, with no contradictory terminal code | Matching broad non-completed status when value is mapped and checked | `NOT_FINAL` only if explicit nonfinal evidence; otherwise `UNKNOWN` | Provisional; individual provider codes not sampled in this phase. |
| Any unrecognized code, missing decisive field, or conflict between fields | `UNKNOWN` | `UNKNOWN` | Safe fallback; create `UNSUPPORTED_STATUS`/`STATUS_CONFLICT`. |

`abstractGameState`, HTTP 200, a score, and an empty event list are never sufficient for `FINAL`. Source state and canonical coverage are separate. If a previously final game reopens or corrects, preserve lifecycle history and reassess coverage/analytics.

## PA play classification and the 76/75 case

`liveData.plays.allPlays[]` is a sequence of provider play objects, **not a guaranteed sequence of official PA**. In observed game 746656, 76 objects include `about.atBatIndex=18`, `result.type=atBat`, `eventType=caught_stealing_2b`, bottom 2nd, with batter 677587. The runner is out before the batter completes a PA. The batter has five play objects but four boxscore PA; excluding that one non-PA play yields 75 candidate PAs matching 75 boxscore PA (E18). Therefore neither `result.type=atBat` nor length of `allPlays` is a PA proof.

Classification has three values: `PA`, `NON_PA`, `UNRESOLVED`. A versioned, explicit outcome dictionary marks only verified terminal batting outcomes as `PA`; observed base-running-only events such as E18 caught stealing are `NON_PA` when pitch/count/play context supports the absence of a completed batter outcome. Unknown/new event types become `UNRESOLVED`, not `NON_PA` or a fabricated PA. A conflicting `result.type`, batter ID, play order, or subsequent PA ownership likewise becomes unresolved. The dictionary must be tested with walks, HBP, sacrifice, interference and substitution cases before a season-wide COMPLETE claim. Preserve the raw play even when classified `NON_PA`.

### Versioned initial classification dictionary (E18 fixture)

For the sampled game 746656, `field_out`, `strikeout`, `walk`, `single`, `double`, `grounded_into_double_play`, `force_out`, `double_play` and `home_run` each correspond to a credited PA; their 75 combined occurrences match per-batter boxscore totals after excluding the single `caught_stealing_2b`. This is the **v0 fixture dictionary for that game**, not a claim that these are all MLB outcomes. The E02 sample additionally demonstrates `hit_by_pitch` as a PA; other outcomes require verified mapping. A new event type always starts `UNRESOLVED`. A `caught_stealing_2b` object is `NON_PA` only when its runner-out/no-completed-batter context and the unique per-batter boxscore reconciliation support that classification; otherwise it is `UNRESOLVED`. If multiple PA/NON_PA assignments could satisfy counts, the game stays unresolved rather than choosing an arbitrary assignment. The dictionary and contextual predicates are versioned inputs to replay.

For each game, compare classified PA candidates with **per-team/per-batter** boxscore `stats.batting.plateAppearances`, not only a global sum. Also check team sums, `atBatIndex` uniqueness/order, batter identity, inning/half, batting team, and HR outcomes. A total match with an individual mismatch does not pass. Normalize `game_pa_ordinal` by ordering only accepted PAs (dense sequence), while retaining raw `(gamePk, atBatIndex)` as source identity. If a source correction changes PA classification, use correction/revision history and reassign ordinals atomically; never silently change PA UUID identity. If two candidate plays claim the same raw key, quarantine rather than choose by arrival order.

## Domain assessment rules

| Domain | `COMPLETE` proof | `PARTIAL` / `UNKNOWN` / `UNAVAILABLE` |
| --- | --- | --- |
| `SCHEDULE` | Approved snapshot for declared target date/range parsed without truncation; expected response structure and all returned game IDs/status fields valid; target-range marker recorded. This proves only the retrieved schedule view, **not** that undisclosed games cannot later be added. | `PARTIAL` for parse/truncation/identity conflict in returned items; `UNKNOWN` before a valid response or after unresolved scope; `UNAVAILABLE` on explicit access loss. Later refresh may add games. |
| `PARTICIPATION` | For the assessed population/scope, every positive appearance claim is reconciled to PA, fielding/action or explicit boxscore evidence; any claimed DNP additionally has affirmative roster/unused-player evidence and complete assessed population. If affirmative population is unavailable, game-wide DNP coverage cannot be COMPLETE, though individual APPEARED rows may be verified. | `PARTIAL` for conflicting player/team state or incomplete population; `UNKNOWN` when DNP population unknown; `UNAVAILABLE` if relevant source unavailable. No boxscore batting row is never a DNP proof. |
| `PLATE_APPEARANCES` | Canonically final; full feed parsed; every play classified PA/NON_PA with zero unresolved; every accepted PA has unique source key, batter/team and deterministic order; per-batter and team PA counts match boxscore; no blocking issue. Player `pa_coverage=COMPLETE` requires that player's team-specific PAs and reported count reconcile within a game whose relevant play classification is reliable. | `PARTIAL` for count mismatch, duplicate key, missing batter, unresolved play, conflicting team or truncated feed; `UNKNOWN` when feed/boxscore absent or finality unknown; `UNAVAILABLE` for explicit source unavailability. A player may be partial even when other players' rows exist. |
| `HR_EVENTS` | Canonically final; PA coverage COMPLETE for affected game; all accepted PA outcomes classified HR/non-HR; every HOME_RUN PA has one HR event and every HR event one PA; per-batter/team boxscore HR totals reconcile with events; no unmatched HR source claim or blocking conflict. | `PARTIAL` for outcome/HR count mismatch, HR without PA or unresolved play; `UNKNOWN` if PA coverage/finality unavailable or HR evidence missing; `UNAVAILABLE` on explicit source loss. `COMPLETE` permits verified zero only if event and boxscore HR counts are both zero. |

Game-wide `PARTICIPATION` completeness is not necessary for a player's **positively evidenced** PA to count, but an uncertain possible batting appearance within a selected window still invalidates that player's window membership as specified in WINDOW_SEMANTICS. `SCHEDULE=COMPLETE` never implies PA/HR completeness. `HR_EVENTS=COMPLETE` must be downgraded when a newer correction invalidates a PA/HR proof. DNP and NOT_WITH_TEAM remain `UNKNOWN` where affirmative evidence is absent. `ZERO_PA_APPEARANCE` requires positive APPEARED evidence **and** complete player PA evidence proving zero; roster presence alone is insufficient.

## Reason codes and known zeros

Reasons are stable machine-readable labels with source references: `SOURCE_REQUEST_FAILED`, `SOURCE_TRUNCATED`, `PARSE_FAILED`, `SCHEMA_DRIFT`, `FINALITY_UNKNOWN`, `UNSUPPORTED_STATUS`, `STATUS_CONFLICT`, `UNRESOLVED_PLAY`, `NON_PA_PLAY_CLASSIFIED`, `MISSING_BATTER`, `DUPLICATE_ATBAT_INDEX`, `BOX_SCORE_PA_MISMATCH`, `BOX_SCORE_HR_MISMATCH`, `HR_WITHOUT_PA`, `TEAM_ATTRIBUTION_CONFLICT`, `ORDER_UNRESOLVED`, `PARTICIPATION_POPULATION_UNVERIFIED`, `ACCESS_NOT_APPROVED`. Informational `NON_PA_PLAY_CLASSIFIED` records the E18 explanation and does not itself block COMPLETE; unresolved classification does. A known zero HR requires finality plus `HR_EVENTS=COMPLETE` after the reconciliation above. Empty arrays, absent player rows and final scores are never zeros by themselves.
